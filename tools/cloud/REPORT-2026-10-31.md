## The set and the base

Each case is one REPL session through `bin/glpc` (the AOT binary), five repetitions, the median; wall, user and system seconds and the maximum resident set from `wait4`.  The scripts: `bench.py` (the timings), `client.dart` and `target.dart` (the profiles: the engine in one process under the VM service, the profiler in another, the measured phase alone sampled).

## The hot spots, by case (JIT runs, the measured phase alone; the shares are of its samples)

**fib_23, the goal (2.5 s JIT).**  ByteRunner.runWithStatus 77% inclusive.  The Dart hash containers take the rest: LinkedHashMap get/find/remove/set/init/insert/rehash together ~40% inclusive, 25% self.  Allocation during the goal, 164 MB (93 MB with tracing on): _List 182k, _Uint32List 68k (the index array of every Map and Set made), _Set 96k, HeapCell 90k, VarRef 83k, _GrowableList 85k, _Closure 49k, _Map 35k, RunnerContext 5.4k sampled.  Where: a RunnerContext per goal run makes six containers (sigmaHat, Si, U, unknownVars, unknownPlaceholders, clauseVars), 80% of the Maps; clauseVars is a Map<int, Object?> keyed by variable index; derefAddr allocates a VarRef on every dereference of an unbound variable (24% of VarRefs), runWithStatus another 53%; bindWriterWithCallbackControl allocates an activations list per bind, empty or not (35% of the GrowableLists), applySigmaHatFCP another 10%; _undecidedMember and _readersOfGoal build Sets per guard (variableOf.values.toSet(), LinkedHashSet.of); BodyKernelRegistry.lookup builds the string '$name/$arity' per spawn (81% of the strings).

**primes_5000, the goal (3.6 s JIT).**  runWithStatus 85%; execGuard 23%, _evaluateGuard 10%, execUnifyVariable 13%, execPutVariable 8%, execGetVariable 6%, execNoMoreClauses 6%; the hash maps ~30% inclusive.  Allocation 44 MB with tracing: _List 110k (58% in runWithStatus, 7% _buildTentativeStructure, 4% applySigmaHatFCP, 4% suspendGoalFCP), HeapCell 58k, _Set 27k, _Map (59% RunnerContext, 26% _undecidedMember, per guard).

**check_gsn, the goal (0.8 s JIT).**  83% of the goal's time is not the check: GlpEngine._post rebuilds the code image on every posted goal, codeImageFromProgram → Artefact.toBytes → encodeCode → encodeInstruction → Artefact._indexOfSignature, a linear scan of the symbol table comparing against ArtefactSymbol.signature, a getter that builds '$name/$arity' on every call: 71% in _indexOfSignature, 61% in string interpolation, 44% in string concatenation.  The scheduler's run of the check itself is 7%.  (The survey's runtime item 33: the image and the runner are rebuilt per postGoal; the survey's wire item 54 wraps _indexOfSignature.)  Allocation 150 MB with tracing: _List 220k (68% ImageSymbol.signature under decodeInstruction), _Closure 271k, _Uint8List 341k, strings 215k (70% Utf8Decoder under the image's parse, 26% ImageSymbol.signature), Token 118k, VarTerm 63k.

**load_app_gsn, the load (7.4 s JIT).**  loadProgram 99%; checkedLinkedProgram 78%; the type checker 76%: buildProgramDFA 62%, checkInstantiationsClosed 60%, _checkProcedure 56%, _instantiateCalls 53%, certifyParametricProcedures (the abstract route) under it.  Self time: Object.hash 7.7%, String.hashCode 5.7%, _concatAll 5.7%, SystemHash.combine 4.9%, _interpolate 3.5%, the maps ~15%, _getFullTypeName, _buildProcedureAutomaton, _addTypeTransitions, TransitionLabel.functor 1.3-1.7% each: the checker keys its maps by strings and records built on the fly, and builds a program DFA per module check.  Allocation 77 MB with tracing: _List 242k, strings 182k --- type_identity.dart's _minimise, _canonicalPrint, _quote, _label and _agreement allocate 67% of the strings and 55% of the lists: the type identity is printed canonically and minimised, string by string, under opaqueEntryOf for every module value (linkedTypeIdentityTables, _moduleValueOf).

**load_graph, the load (2.8 s JIT).**  The same profile: the type checker 71%, _checkProcedure 60%, _instantiateCalls 47%, buildProgramDFA 42%, certifyParametricProcedures 39%; String.hashCode 6.4%, Object.hash 4.5%, _concatAll 3.6%; TransitionLabel 96k and _Record 96k allocated; type_identity.dart's canonical print and minimisation 60% of the strings and lists.

## What the base says

1. The engine's time is in Dart's hash containers, made and torn down per goal and per guard, not in the instructions: six containers per RunnerContext, a Map for the clause's variables, a Set per guard evaluation, a list per bind, a VarRef per dereference, a string per kernel lookup.
2. A posted goal pays for the whole program's serialisation and parse before it runs; on a large program the goal is a tenth of its own wall time.  The serialisation's symbol lookup is linear with a string built per comparison.
3. The pipeline's time is the type checker: the program DFA built per module, the call instantiation search, and the type identity's canonical print and minimisation over strings; string hashing and concatenation are the self time.
4. Memory: fib(23) reaches 217 MB resident without a garbage collection (the VM's log shows none), the new space growing to hold what the goal allocates.

Each of these is measurable by this set; an optimisation is reported with the case's median before and after.  None is taken up without Code's word; the first to propose is 2, the image built once per load set, which changes no behaviour and is the survey's runtime item 33.
