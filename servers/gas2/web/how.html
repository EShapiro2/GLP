How GAS2 works

GAS2 follows the main branch of GLP's repository. Every hour it reads every grassroots contract there, works out how the contracts relate, takes each one down the cascade to a mini-app of the Grassroots Super-App, and runs that mini-app on two super-apps. Each step uses GLP's own tools, so the site always shows what the repository can do at that moment.

From a contract to a mini-app

A contract is written in plain English, its clauses, and as act schemas. GAS2 takes the steps that GLP's programs/apps/compile.sh takes for the apps written there by hand:

StepWhat it givesGLP's tool

The mini-app is the platform plus the files every app in programs/apps has. These are the entry miniapp/4, which is the same file in every app, the platform's types written again, and a scripted person. GAS2 writes them out for each contract, using GLP's own files with only the contract's name and a short script put in. No contract needs code written by hand to become a mini-app. Where one does not get there, the contract's page says which step stopped it and why, in the tool's own words.

A run on two super-apps

Each run starts two smartphones, Alice's and Bob's, as two isolates of GLP's runtime. Each runs the super-app, the program in programs/social/graph/core, under its own key pair. Each person's acts on their super-app are scripted, and so are their acts in the mini-app:

  1. Each person trusts the compiler's key. Each installs the mini-app, and the super-app installs it only if its certificate is from a trusted compiler and its creator certified it as grassroots.
  2. Alice asks to be Bob's friend, and Bob says yes. They are now friends in the social graph, and each holds the attestation of their friendship, signed under their own key.
  3. Alice invites Bob to the mini-app with a signed invitation, and Bob, who said yes in advance, joins.
  4. At the handshake each side signs an undertaking to keep the contract. They compare the mini-app's source identity and the type identity of its entry, and only then does the conversation open.
  5. The super-app activates the mini-app with its grants: the person's key, the person's screen, and the channel to the social graph. In the mini-app, each person establishes an identity, and Alice proposes that the two know each other, which Bob accepts.

For the contracts whose apps are written by hand in programs/apps, the contract's page also runs that app's own play, with its longer scripts.

On a device

GAS2's app (get it here) runs the same super-app, programs/social/graph/core, for a real person, with GAS2's device harness in place of the super-app's own entry superapp/3. The two differ in one thing: a mini-app the person installs is shown to the person.

In GLP the super-app holds a mini-app's person channel at the type Opaque and can only pass it on, so nothing outside the mini-app can write the person's input into it. So each of GAS2's mini-apps carries a live person of its own. The super-app runs it at the mini-app's own types, as the plays run their scripted persons. It shows the person every draw the mini-app makes, and reads the person's answers back from strings the device writes.

Each device certifies its mini-apps under the person's own key, so the person trusts their own compiler. Friendship, the invitation, the undertakings and the handshake are the super-app's, as in the runs above. On a phone the super-app's network is GNA's layer, Bluetooth and the local network, so the people near show on the page and are added with one tap; people not near are reached through talmonlab's relay, encrypted end to end. A computer uses the relay alone.

On the web (for iPhones, where there is no app yet) the same page and the same super-app run for the person on talmonlab's server, over the relay. The server holds the person's key, and the page says so.

The app maker (here) takes a contract a person writes, its text and its act schemas, down the same cascade, and gives a link. A device that opens the link adds the mini-app and certifies it under its own person's key, like the ones it came with.

How the relations are found

GSC defines five relations between contracts. Three are about schemas: amends deletes and adds schemas, extends amends while deleting nothing, and instantiates fills in a parametric contract's parameters. Two are about runs: implements, and restricts, which allows only runs of the base. Each contract's text names what it builds on. Where the text also says how, for example "GD-S restricts GD", the map shows that.

Otherwise GAS2 compares the two contracts' schemas, as GSC's reader reads them, with their variables renamed in order. If every schema of the base is kept unchanged, then the contract extends it. If some are deleted or replaced, then it amends it, and the contract's page says which. Whether one contract restricts another cannot be decided in general (GSC, Proposition "Restriction is undecidable"), so restriction is shown only where a contract's text states it.

Where it lives

The code is servers/gas2 on the GAS2 branch of nimrodtalmon/GLP. It keeps two working copies of GLP's main branch and builds the new head in one while serving the other, switching only when a build is complete. Its state is at api/status.
