## 1. Overview

This document specifies **Implementation-Ready Multiagent GLP (irmaGLP)**, combining the implementation-ready structure of irGLP with the multiagent framework of maGLP. While irGLP provides deterministic scheduling and suspension management for single agents, and maGLP defines cross-agent communication through shared variables, irmaGLP specifies the concrete data structures and message-passing mechanisms suitable for multiagent smartphone implementation.

### 1.1 Variable Locality

A variable X is **local** to agent p if X occurs in p's resolvent. Non-local variables require coordination through variable tables and explicit message passing, replacing maGLP's abstract shared-variable communication with concrete routing mechanisms.

### 1.2 Fundamental Invariant

Assignments produced by Reduce transactions are immediately applied if the reader is local, otherwise they become messages routed through the variable tables.

## 2. Transition System

**Definition [Implementation-Ready maGLP Transition System]**

The implementation-ready maGLP transition system over agents P ⊂ Π and GLP module M is the multiagent transition system IRmaGLP = (C, c₀, T) where:

- **C** is the set of all configurations where for each p ∈ P, the local state c_p is an implementation-ready resolvent (Definition 3.1)
- **c₀** is the initial configuration where for each p ∈ P:
  - R_p = ([agent(p, ch(_?, _), ch(_?, _))], ∅, ∅)
  - V_p = ∅
  - M_p = ∅
- **T** is the union of all transitions generated by:
  - Unary Reduce transactions for each p ∈ P (Section 5.2)
  - Binary Communicate transactions for each (p, q) ∈ P × P, p ≠ q (Section 5.3)
  - Binary Network transactions for each (p, q) ∈ P × P, p ≠ q (Section 5.4)

## 3. Local State Structure

### 3.1 Implementation-Ready Local State

**Definition [Implementation-Ready maGLP Local State]**

The local state of agent p ∈ Π is an implementation-ready resolvent s_p = (R_p, V_p, M_p) where:

#### 3.1.1 Resolvent R_p = (A_p, S_p, F_p)

Separates resolvent goals into three types:

- **Active**: A_p ∈ 𝒜* (FIFO queue)
- **Suspended**: S_p ⊆ 𝒜 × 2^(V?) (pairs of atom and blocking readers)
- **Failed**: F_p ⊆ 𝒜 (terminal)

The resolvent R_p partitions goals into three categories. Active goals A_p contains a queue of goals to be reduced in FIFO order. Suspended goals S_p pairs each atom with the set of readers preventing its reduction—for (A, W) ∈ S_p, the set W contains all readers from the suspension sets across all clause attempts. When any reader X? ∈ W receives a value or is abandoned, A moves to the tail of A_p. Failed goals F_p contains atoms for which every reduction attempt either failed outright or suspended only on abandoned variables.

#### 3.1.2 Variable Table V_p

V_p ⊆ 𝒱 × Π × (𝒯 ∪ Π ∪ {⊥}) maintains shared variable state as a set of triples where each (Y, q, s) ∈ V_p:

- **Created Writer**: Y ∈ V, q = p, s ∈ 𝒯 is the value of Y, else s = ⊥
- **Imported Writer**: Y ∈ V, q ≠ p, s ∈ 𝒯 is the value of Y, else s = ⊥
- **Created Reader**: Y ∈ V?, q = p, s ∈ Π is the read-requesting agent, else s = ⊥
- **Imported Reader**: Y ∈ V? (reader), q ≠ p, s = q indicates a read request has been sent from p to q, else s = ⊥

The variable table V_p maintains shared variables where one element of each reader/writer pair is local to p while its counterpart is non-local. For writers (both created and imported), the table stores the creator and any assignment to enable response to read requests. For created readers, it records which agent has requested the value. For imported readers, it tracks whether a read request has been sent to the creator. This unified structure ensures variables referenced by non-local counterparts are not prematurely garbage collected and provides routing information for cross-agent communication.

**Invariant**: V_p contains exactly those variables whose paired counterparts are non-local. When p receives a term containing a variable from V_p, that variable becomes local and must be removed from V_p. When p exports a term, the export helper function updates V_p accordingly: variables created by p are added when first exported, while variables created by others are removed (except for requested readers which require relay variables).

#### 3.1.3 Message Queue M_p

M_p is a set of pending messages as pairs (content, destination) where destination q ∈ Π:

- Assignments: (X?:=T, q)
- Read requests: (request(X?, p), q) where p requests X? from q
- Abandonment notifications: (abandon(X), q)

## 4. Helper Routines

Helper routines for implementation-ready transactions, agent p. All routines may modify V'_p and M'_p.

### 4.1 abandon(Y)

The abandon helper notifies other agents when variable Y becomes unreachable. For imported variables, it notifies the creator q. For created readers with a requester s, it notifies that requester. The paired variable Y' is sent in the message to indicate which part of the pair was abandoned.

**Definition [routine abandon(Y)]**

- If (Y, q, s) ∈ V_p where q ≠ p: remove from V'_p and add (abandon(Y'), q) to M'_p
- If (Y, p, s) ∈ V_p and s ≠ ⊥: remove from V'_p and add (abandon(Y'), s) to M'_p
- Otherwise: just remove (Y, ·, ·) from V'_p if present

where Y' = Y? if Y ∈ V, else Y' = Y if Y ∈ V? (the paired variable)

### 4.2 request(X?)

The request helper sends a read request for an imported reader that hasn't been requested yet. It updates the table entry from (X?, q, ⊥) to (X?, q, q) to record that the request was sent, preventing duplicate requests.

**Definition [routine request(X?)]**

If (X?, q, ⊥) ∈ V'_p and q ≠ p then:
- Update to (X?, q, q) in V'_p
- Add (request(X?, p), q) to M'_p

### 4.3 export(T) returns T'

The export helper updates the variable table when term T is sent outside agent p. Variables created by p are added to V_p when first exported. Imported variables are typically removed since they're no longer local, except for requested readers which require special handling: a fresh relay pair (Z, Z?) is created with a forwarding goal to maintain the request relationship while allowing the original reader to leave p's scope.

**Definition [routine export(T) returns T']**

Set T' := T

For each variable Y occurring in T:
- **Local**: If Y created by p and (Y, p, ·) ∉ V'_p: add (Y, p, ⊥) to V'_p
- **Non-local**: If Y created by q ≠ p then:
  - **Writer or Non-requested Reader**: If Y ∈ V or (Y, q, ⊥) ∈ V'_p then remove (Y, q, ·) from V'_p
  - **Requested Reader**: If (Y, q, q) ∈ V'_p then create fresh pair (Z, Z?), replace Y with Z? in T', add export_reader(Y, Z) to A'_p, add (Z?, p, ⊥) to V'_p

T' is the result of applying variable replacements (if any) to T.

The `export_reader` goal spawned by the export helper is a simple forwarding process that waits for the original reader to receive its value and then assigns that value to the relay writer:

```prolog
export_reader(Y?, Z) :- Z = Y?.
```

This ensures that when the creator eventually binds the original variable, the value flows through the relay to the new recipient.

### 4.4 reactivate(X?) returns R

**Definition [routine reactivate(X?) for agent p returns R]**

- Let R = {G : (G, W) ∈ S'_p, X? ∈ W}
- S'_p := S'_p \ {(G, W) : G ∈ R}
- Return R

## 5. Transactions

### 5.1 Variable Abandonment

During goal reduction, variables may become abandoned when their paired counterparts disappear from the computation without being instantiated. This happens when a variable that occurs in the reduced atom is neither instantiated by the reduction nor occurring in the resulting body. The implementation should detect such abandonment to prevent indefinite suspension or shared-variable entries for variables that can never receive values. Abandoned variables allow garbage-collection in shared variable tables and cause dependent suspended goals to fail rather than wait indefinitely.

**Definition [Variable Abandonment in Reduction]**

When reducing atom A with clause C yielding body B and substitution σ̂, a variable Y is **abandoned** if its paired variable Y' satisfies all three conditions:
1. Y' occurs in A
2. Y' is not instantiated by σ̂ or σ̂?
3. Y' does not occur in B

### 5.2 Reduce Transaction (Unary)

**Definition [Implementation-Ready Reduce Transaction]**

The unary Reduce transaction for agent p transitions (R_p, V_p, M_p) → (R'_p, V'_p, M'_p) where R_p = (A_p, S_p, F_p), (R'_p, V'_p, M'_p) := (R_p, V_p, M_p) with A_p = A · A_r for head goal A:

#### Case 1: Reduce

If GLP reduction of A with first applicable clause C ∈ M succeeds with (B, σ̂):

- Let R = ⋃_{X? ∈ V_σ̂?} reactivate(X?) (modifies S'_p)
- A'_p := (A_r · B · R)σ̂σ̂?
- Update V'_p: for each X? ∈ W where (X?, q, ⊥) ∈ V'_p, update to (X?, q, q)
- Update M'_p for created readers: add (X?:=T, r) for each {X?:=T} ∈ σ̂? where (X?, p, r) ∈ V'_p, r ≠ ⊥
- **Update M'_p for imported writers**: add (X?:=T, q) for each {X:=T} ∈ σ̂ where (X, q, ·) ∈ V'_p, q ≠ p
- Call abandon(Y) for each abandoned variable Y

#### Case 2: Suspend

Else if W = ⋃_{C ∈ M} W_C ≠ ∅:

- A'_p := A_r
- S'_p := S'_p ∪ {(A, W)}
- Call request(X?) for each X? ∈ W (modifies V'_p and M'_p)

#### Case 3: Fail

Else:

- A'_p := A_r
- F'_p := F'_p ∪ {A}
- Call abandon(Y) for each variable Y in A (modifies V'_p and M'_p)

Then R'_p := (A'_p, S'_p, F'_p).

### 5.3 Communicate Transaction (Binary)

**Definition [Implementation-Ready Communicate Transaction]**

The binary Communicate transaction (c_p, c_q) → (c'_p, c'_q) where p ≠ q and (m, q) ∈ M_p. Set (c'_p, c'_q) := (c_p, c_q), remove (m, q) from M'_p, and case:

#### Type 1: Assignment

m = (X?:=T):

- **If X? is local to q** (i.e., (X?, ·, ·) ∉ V'_q):
  - Let R = reactivate(X?) for agent q (modifies S'_q)
  - If T ≠ ⊥: A'_q := (A_q · R){X?:=T}, and apply {X?:=T} to S'_q and F_q
  - Else: A'_q := A_q · R
  - For each variable Y in T not already local to q and created by r: add (Y, r, ⊥) to V'_q

- **Else if (X?, q, r) ∈ V'_q where r ≠ ⊥** (created reader with pending request):
  - Forward assignment: add (X?:=T, r) to M'_q
  - Update entry: (X?, q, r) → (X?, q, T) in V'_q

- **Else if (X?, q, ⊥) ∈ V'_q** (created reader, no request yet):
  - Store value: update to (X?, q, T) in V'_q

#### Type 2: Read Request

m = request(X?, p):

- If p = ⊥ then call abandon(X?) for agent q (modifies V'_q and M'_q)
- Else if (X?, q, T) ∈ V'_q where T ∈ 𝒯 (value already stored): add (X?:=T, p) to M'_q
- Else if (X?, q, ⊥) ∈ V'_q: update to (X?, q, p) in V'_q
- Else if (X, q, T) ∈ V'_q then add (X?:=T, p) to M'_q

### 5.4 Network Transaction (Binary)

**Definition [Implementation-Ready Network Transaction]**

The binary Network transaction (c_p, c_q) → (c'_p, c'_q) where p ≠ q and a new msg(q, X) appears in p's network output stream. Set (c'_p, c'_q) := (c_p, c_q):

- Let X' := export(X) for agent p (modifies V'_p and M'_p)
- Add X' to q's network input stream
- For each variable Y in X' not already local to q and created by r: add (Y, r, ⊥) to V'_q

### 5.5 Scheduling

The scheduler operates deterministically by selecting the head of the active queue A_p. When any reader X? ∈ W for a suspended goal (A, W) ∈ S_p receives a value or is marked abandoned, the goal A is moved from S_p to A_p for re-evaluation. Goals in F_p remain terminal, preserving logical completeness while enabling runtime fault analysis.

## 6. Example Scenarios

The following scenarios illustrate how the variable table and message routing mechanisms work together to support cross-agent communication, including the friend-mediated introduction protocol.

### 6.1 Scenario 1: Direct Communication

Alice sends a message to her friend Bob through an established channel.

**Initial State**

Alice holds writer W for Bob's input channel; Bob holds paired reader W?.

- V_alice = {(W, alice, ⊥)} — created writer, reader is non-local
- V_bob = {(W?, alice, ⊥)} — imported reader from alice

**Step 1: Bob suspends on W?**

Bob's goal needs the value of W?, causing suspension.

- Bob calls request(W?): updates (W?, alice, ⊥) → (W?, alice, alice)
- Bob sends (request(W?, bob), alice) to Alice

**Step 2: Alice receives request**

Alice processes the read request.

- Alice updates (W, alice, ⊥) → (W, alice, bob) — records Bob as requester

**Step 3: Alice binds W**

Alice's reduction binds W := T for some term T.

- Alice sees (W, alice, bob) with requester bob ≠ ⊥
- Alice sends (W?:=T, bob) to Bob

**Step 4: Bob receives assignment**

Bob processes the assignment, W? is local.

- Bob applies {W?:=T} to resolvent
- Bob removes (W?, ·, ·) from V_bob
- Suspended goals reactivate

### 6.2 Scenario 2: Friend-Mediated Introduction

Bob introduces Alice to Charlie by creating a shared channel and distributing its endpoints. This scenario demonstrates imported writers and the creator-as-routing-hub pattern.

**Initial State**

Bob knows both Alice and Charlie; they don't know each other.

- V_alice = V_charlie = V_bob = ∅ (for the new channel)

**Step 1: Bob creates channel**

Bob executes `new_channel(ch(AC?, CA), ch(CA?, AC))` creating:

- Writer CA and reader CA? (Alice → Charlie direction)
- Writer AC and reader AC? (Charlie → Alice direction)

All four variables are initially local to Bob.

**Step 2: Bob exports to Alice**

Bob sends `ch(AC?, CA)` to Alice via export.

- Bob adds (AC?, bob, ⊥) and (CA, bob, ⊥) to V_bob
- Alice imports: adds (AC?, bob, ⊥) and (CA, bob, ⊥) to V_alice

Alice now holds: reader AC? (to receive from Charlie) and writer CA (to send to Charlie).

**Step 3: Bob exports to Charlie**

Bob sends `ch(CA?, AC)` to Charlie via export.

- Bob adds (CA?, bob, ⊥) and (AC, bob, ⊥) to V_bob
- Charlie imports: adds (CA?, bob, ⊥) and (AC, bob, ⊥) to V_charlie

Charlie now holds: reader CA? (to receive from Alice) and writer AC (to send to Alice).

**Variable Table Summary After Introduction**

- V_bob = {(AC?, bob, ⊥), (CA, bob, ⊥), (CA?, bob, ⊥), (AC, bob, ⊥)}
- V_alice = {(AC?, bob, ⊥), (CA, bob, ⊥)} — both imported from bob
- V_charlie = {(CA?, bob, ⊥), (AC, bob, ⊥)} — both imported from bob

Bob is the creator of all channel variables and serves as the routing hub.

**Step 4: Charlie requests CA?**

Charlie's goal needs the value of CA?.

- Charlie calls request(CA?): sends (request(CA?, charlie), bob)
- Charlie updates (CA?, bob, ⊥) → (CA?, bob, bob)

**Step 5: Bob receives request**

Bob processes Charlie's read request for CA?.

- Bob has (CA?, bob, ⊥) — created reader, no value yet
- Bob updates (CA?, bob, ⊥) → (CA?, bob, charlie) — records Charlie as requester

**Step 6: Alice binds CA**

Alice sends a message by binding writer CA := T.

- Alice has (CA, bob, ⊥) — imported writer from bob
- Since bob ≠ alice, Alice sends (CA?:=T, bob) to the creator

**Step 7: Bob receives assignment, forwards to Charlie**

Bob processes assignment for CA?.

- Bob has (CA?, bob, charlie) — created reader with pending request
- Bob forwards: sends (CA?:=T, charlie)
- Bob updates (CA?, bob, charlie) → (CA?, bob, T) — stores value

**Step 8: Charlie receives value**

Charlie processes assignment for CA?, which is local to Charlie.

- Charlie applies {CA?:=T} to resolvent
- Charlie removes (CA?, ·, ·) from V_charlie
- Suspended goals reactivate

**Key Insight: Creator as Routing Hub**

The creator (Bob) maintains entries for all channel variables and routes values from writers to readers:

1. Alice binds imported writer → notifies creator Bob
2. Bob receives value, checks for pending request → forwards to Charlie
3. Charlie receives value at local reader

This pattern enables introduction without requiring Alice and Charlie to communicate directly until after the introduction completes.

### 6.3 Scenario 3: Request Arrives After Value

If Alice binds CA before Charlie requests CA?:

**Step 6': Alice binds CA early**

- Alice sends (CA?:=T, bob) to creator

**Step 7': Bob receives assignment, no request yet**

- Bob has (CA?, bob, ⊥) — no requester
- Bob stores value: updates (CA?, bob, ⊥) → (CA?, bob, T)

**Step 4': Charlie requests CA? later**

- Charlie sends (request(CA?, charlie), bob)

**Step 5': Bob receives request, value already stored**

- Bob has (CA?, bob, T) where T ∈ 𝒯
- Bob immediately replies: sends (CA?:=T, charlie)

The order of assignment and request does not matter; the creator stores whichever arrives first and completes the exchange when both are present.

## 7. Extensions for Secure Multiagent GLP

To extend the implementation-ready transition system to Secure maGLP, the following cryptographic mechanisms augment the definitions without modifying their structure.

### 7.1 Agent Identity and Cryptography

Each agent p ∈ Π is augmented with:

- A self-chosen keypair (pk_p, sk_p) where the public key pk_p serves as the agent's identity
- The agent identifier p is synonymous with pk_p throughout the system
- We assume knowledge of other agents' public keys through social contacts

### 7.2 Message Authentication and Encryption

All messages in M_p are cryptographically protected. A message (m, q) ∈ M_p becomes (m_{M,p,q}, q) where the subscript notation indicates:

- M: Attestation by the GLP runtime proving m resulted from correct execution of module M
- p: Digital signature using agent p's private key sk_p
- q: Encryption using agent q's public key pk_q

### 7.3 Transaction Augmentations

**Reduce Transaction**: When generating messages (X?:=T, r) for remote readers, the implementation creates (X?:=T)_{M,p,r} with attestation proving the assignment resulted from correct goal/clause reduction using module M.

**Communicate Transaction**: Before processing any received message (m_{M,p,q}, q):
1. Decrypt using q's private key sk_q
2. Verify signature using p's public key pk_p
3. Validate attestation for module M
4. Discard the message if any verification fails
5. Process according to Definition 5.3 only if all verifications succeed

**Network Transaction**: Network messages msg(q, X) are similarly protected as (msg(q, X))_{M,p,q} ensuring authenticated channel establishment.

### 7.4 Module Verification

- Each agent executes a verified GLP module M with a cryptographic hash identifier
- Attestations include the module hash, enabling recipients to verify code compatibility
- Guard predicates `attestation(X, att(Agent, Module))` and `module(M)` provide program-level access to verification results

### 7.5 Security Properties Achieved

These extensions ensure:

- **Integrity**: Messages cannot be modified without detection
- **Confidentiality**: Only intended recipients can decrypt messages
- **Non-repudiation**: Senders cannot deny authenticated messages
- **Authentication**: All inter-agent communication is mutually authenticated

The implementation-ready transition system with these cryptographic extensions realizes Secure maGLP while maintaining the same operational behaviour for correctly authenticated participants. Byzantine agents who fail verification are effectively excluded from the computation through message rejection.

## 8. Implementation Notes

*Note: This section contains implementation guidance not derived from the paper.*

### 8.1 Global Variable Identity

Variables crossing agent boundaries need globally unique identifiers for routing.

**Format**: `creator:localId`

- creator ∈ Π: agent who allocated this variable
- localId: unique integer within creator's heap

**Example**: `alice:1042` identifies variable with local ID 1042 created by alice.

When serializing terms for inter-agent transport, local variable IDs are replaced with global IDs.

### 8.2 Data Structures

- **Active Queue**: FIFO queue (e.g., `Queue<Goal>` in Dart)
- **Suspended Set**: Map from readers to goals (e.g., `Map<int, Set<Goal>>`)
- **Variable Table**: Map from varId to entry (e.g., `Map<int, VarEntry>`)
- **Message Queue**: Queue per destination (e.g., `Map<AgentId, Queue<Message>>`)

### 8.3 Serialization

Terms must be serialized to bytes for inter-agent transport:

1. **Constants**: Type tag + value bytes
2. **Variables**: Type tag + global ID string
3. **Structures**: Type tag + functor + arity + serialized args
4. **Lists**: Convert to structure form, then serialize

**Round-trip requirement**: deserialize(serialize(T)) ≡ T (up to variable renaming)

### 8.4 Scheduler-IRMA Integration

The Reduce transaction (Section 5.2) modifies both the resolvent R_p and the variable/message structures V_p/M_p atomically. In a modular implementation where the scheduler and IRMA context are separate components:

**On suspension (Case 2):**
- The scheduler must provide the set of blocking readers W to the IRMA layer
- The IRMA layer then calls `request(X?)` for each X? ∈ W
- This may be implemented either as a callback during suspension or by returning W from the drain operation

**Implementation approach:**

The `DrainResult` structure should include the blocking reader set:

```
DrainResult {
  goalsRan: List<int>
  status: ExecutionStatus  // succeeded | failed | suspended
  suspendedGoals: List<String>  // for debugging/display
  blockingReaders: Set<int>  // varIds of readers causing suspension
}
```

After each drain operation, if `status == suspended`, the caller should invoke:

```
context.processSuspension(result.blockingReaders)
```

This ensures read requests are sent for imported readers per Section 5.2 Case 2, while maintaining separation between the scheduler (which tracks goal execution) and the IRMA context (which manages V_p/M_p).
